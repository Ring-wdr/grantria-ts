# 2.5D 전환 기획 (악튜러스·라그나로크 방식)

목표: 지금의 2D 포트를 그대로 두고, **3D 지형 위에 2D 스프라이트 캐릭터를 세우는** 2.5D 버전을 만든다.
기준은 악튜러스(고정 쿼터뷰 카메라 + 3D 배경 + 2D 캐릭터)와 라그나로크(3D 맵 + 빌보드 스프라이트 + 2D 셀 이동 판정)다.
파이널판타지7(프리렌더 배경)이나 리틀 나이트메어(3D 캐릭터, 횡스크롤 깊이)는 대상이 아니다.

| 유지 | 바꿈 | 추가 |
|---|---|---|
| Tauri 2 크로스 플랫폼, three.js, WebGL, Vite, XState | 필드 렌더러(`web/render/field.ts`)를 3D 씬으로 교체 | 맵별 3D 데이터(높이, 타일 분류, 오브젝트 배치 방식) |
| `src/core` 전체: 스토리 분기, 스탯, 강화, 상점, 던전(차원의 문·심연), 퀘스트, 세이브 | 카메라(2D 스크롤 → 3D 추적 카메라) | 대쉬(이동 + 짧은 무적) |
| 20 FPS 고정 틱, 2D 픽셀 좌표계, 통행 레이어, 히트박스 | 월드 좌표에 붙는 UI 조각(머리 위 숫자, 퀘스트 마크)의 위치 계산 | 맵 3D 편집 도구(기존 맵 뷰어 확장) |
| DOM UI(메뉴·HUD·대화), 2D 원본 스프라이트·이펙트 에셋 | | |

## 1. 핵심 원칙: "로직은 2D, 그림만 3D"

라그나로크도 서버·클라이언트 판정은 2D 셀 격자(GAT)로 하고 지형 높이는 그림에만 쓴다. 같은 방식을 쓴다.

```
          core (변경 거의 없음)                         web/render3d (신규)
 ┌──────────────────────────────────┐        ┌───────────────────────────────────────┐
 │ Player / Monster / Boss / Event   │        │  월드 좌표 (x, y)  →  3D (X, Y, Z)     │
 │ 좌표: 월드 픽셀 (x, y)             │ Drawable│     X = x                              │
 │ 판정: 16px 통행 셀, 2D 사각형 박스  │ ──────▶ │     Z = y                              │
 │ 깊이: 없음 (렌더러가 결정)          │        │     Y = height(x, y)  (높이맵 샘플)     │
 └──────────────────────────────────┘        │  지형 메시 + 빌보드 스프라이트 + 이펙트   │
                                              └───────────────────────────────────────┘
```

- `core`의 좌표·판정·AI·이벤트 스크립트·경로 탐색은 손대지 않는다. 몬스터 패턴, 보스 14종, 히트박스, 넉백이 원본 그대로 동작하고 기존 테스트가 그대로 통과해야 한다.
- 높이는 **렌더링 전용**이다. 언덕 위에 있어도 판정은 평면이다(라그나로크와 같음). 높이 차가 큰 곳(절벽)은 원본 맵에서 이미 통행 불가 셀이라 판정과 그림이 어긋나지 않는다.
- 세이브 형식, 원본 세이브 변환, 슬롯 데이터는 바뀌지 않는다. 2D 버전과 2.5D 버전이 같은 세이브를 읽는다.
- 이 저장소의 경계(`Drawable`, `InputState`, `Platform`)가 이미 "다른 렌더러를 붙이는" 용도로 설계되어 있다(`architecture.md`). 2.5D 렌더러는 그 경계에 붙는 새 렌더러다.

## 2. 저장소 전략: 지금 저장소를 그대로 두는 방법

추천: **이 저장소를 포크한 `grantria-25d`를 만들고, 이 저장소를 `upstream` 원격으로 둔다.**

- 2.5D 작업은 새 디렉터리(`src/web/render3d/`, `tools/map3d/`, `public/map3d/`)와 몇 개의 연결 지점에만 들어간다. `core` 수정은 대쉬 하나(§6)뿐이고, 그것도 옵션으로 막을 수 있게 만든다.
- 그래서 2D 쪽 버그 수정·기능(`core`, `web/game`)은 `git merge upstream/main`으로 계속 받아온다. 충돌 지점은 `fieldScene.ts`의 그리기 부분과 렌더러 생성 부분으로 좁혀 둔다.
- 대쉬처럼 2D에도 쓸 만한 `core` 변경은 이 저장소에 먼저 넣고(기본 꺼짐) 포크가 받아가면 충돌이 없다.
- 포크 대신 한 저장소에 `game3d.html` 엔트리를 추가하는 방법도 가능하지만, "지금 저장소는 그대로"라는 조건에서는 포크가 맞다. 나중에 2.5D가 안정되면 한 저장소에서 렌더 모드 전환(`옵션: 2D / 2.5D`)으로 합칠 수 있도록 연결 지점을 인터페이스로 만든다(§3.1).

## 3. 렌더링 구조

### 3.1 연결 지점: `FieldRenderer` 인터페이스

지금 `fieldScene.ts`는 `Field`(2D)를 직접 쓰고, 월드 좌표에 붙는 UI는 `x - camX` 식으로 화면 좌표를 계산한다. 이 두 곳을 인터페이스로 뺀다.

```ts
interface FieldRenderer {
  load(mapId: number): Promise<void>;          // FieldMap.loadData + 그래픽 준비
  render(cam: CameraState, ents: Drawable[], overlay?: (L: WorldLayer) => void): void;
  project(x: number, y: number, lift?: number): [sx: number, sy: number] | null;   // 월드 → 480×320 화면
  dispose(): void;
}
```

- 2D 구현(`Field`)은 지금 코드 그대로 `project = (x, y) => [x - camX, y - camY]`.
- 3D 구현(`Field3D`)은 three.js 씬을 그리고 `project`는 카메라 투영.
- `fieldScene.ts`의 `drawQuestMarks`, `drawStatus`, 채집 이펙트, 말풍선(`drawBalloons`)처럼 `x - ox`를 쓰는 곳을 모두 `project()`로 바꾼다. 이 작업만 끝나면 `fieldScene`은 렌더러가 2D인지 3D인지 모른다.
- `beforeTop` 콜백(워프 이펙트, 버프 오라, 게이트 배너)은 `WorldLayer`로 받아, 월드 좌표에 붙는 것(오라, 워프)은 3D 빌보드로, 화면 고정인 것(게이트 배너, `V.zoom`)은 화면 패스로 보낸다.

### 3.2 패스 구성

```
1. 3D 패스 (깊이 버퍼 사용, 저해상도 타깃)
   ├─ 지형 메시 (타일 텍스처, 높이)          : 불투명
   ├─ 바닥 데칼 (objBg / objLow, 그림자)       : 지형 위에 붙인 평면
   ├─ 세운 오브젝트 (objMid: 나무, 기둥, 집)   : 알파 테스트 + 깊이 쓰기
   ├─ 캐릭터·몬스터·NPC·투사체 빌보드          : 알파 테스트 + 깊이 쓰기
   └─ 반투명 파츠(alpha8 < 8, 가산 등 고정 블렌드): 뒤→앞 정렬, 깊이 쓰기 없음
2. 이펙트 패스 (기존 SpriteLayer + Compositor 재사용)
   └─ 대상 색을 읽어야 하는 원본 블렌드 모드 이펙트: 월드 위치를 project()로 화면에 찍어 기존 방식 그대로
3. 화면 필터 (그대로): 낮/밤 색조, 흑백, 이벤트 screenFx(RGB565), 흔들림, 메뉴 배경 블러
4. DOM UI (그대로)
```

- 원본 블렌드 모드 중 고정 함수로 되는 것은 3D 패스에서 바로, 대상 픽셀 스냅샷이 필요한 것만 2번 패스로 보낸다. `sprites.ts`의 `blendSetup()`이 이미 둘을 구분하므로 그 판정을 그대로 쓴다. 2번 패스 이펙트는 벽에 가려지지 않지만, 라그나로크도 스킬 이펙트는 지형 위에 그리므로 문제가 되지 않는다.
- **해상도**: 3D 패스는 480×320(풀스크린 여백 포함)의 정수배(기본 2배 960×640)에 그리고 Nearest로 키운다. 도트가 흐려지지 않고, 모바일 GPU 부담도 작다. 텍스처는 전부 `NearestFilter`, 밉맵 없음.
- **스프라이트 렌더링**: `SpriteLayer`의 cmf 프레임 조립(파츠 dx/dy, 회전, 반전, 장비 레이어 w/h/a/p, 틴트·페이드)은 그대로 쓰고, 버텍스 위치만 "화면 평면" 대신 "빌보드 평면(발 위치 기준)"에 낸다. 즉 `SpriteLayer`에 출력 좌표 변환 하나를 주입하는 형태로 확장한다.
- **깊이 정렬**: 지금의 `depthSort`(y 기준, 동률이면 액터 먼저)는 3D에서 깊이 버퍼가 대신한다. 도트 스프라이트는 알파가 0/1이므로 `alphaTest 0.5 + depthWrite`로 정렬 없이 겹침이 맞는다. 같은 깊이의 빌보드끼리 깜빡이지 않도록 원본 정렬 키(`actorDepth`)를 아주 작은 깊이 오프셋으로 넣는다.
- **그림자**: `shadow.pxl` 곱하기 → 지형 위에 붙인 데칼 사각형(높이맵 따라 기울임). 원본처럼 스프라이트 틴트·페이드는 받지 않는다.

### 3.3 카메라

| 항목 | 기본값(악튜러스형) | 옵션(라그나로크형) |
|---|---|---|
| 투영 | 원근, 좁은 화각(FOV 20~25°) — 화면 위아래 스프라이트 크기 차가 작다 | 같음 |
| 피치 | 50° 내려다봄 | 35~65° 조절 |
| 요(회전) | 고정(북쪽이 화면 위) | ±20° 흔들기만 허용 (§3.4 이유) |
| 줌 | 원본과 같은 픽셀 배율이 되는 거리 | 0.75~1.5배 |
| 추적 | 기존 `updateCamera()`의 지연·선행 공식을 그대로 쓰고, 결과 (camX, camY)를 바라보는 점으로 변환 | 같음 |

- 원본 카메라 공식(`fieldScene.updateCamera`, 맵 경계 클램프, 이벤트 카메라 `eventCamera`, 흔들림)은 2D 좌표로 계속 계산한다. 렌더러는 "2D 화면 중심점 → 3D 바라보는 점(높이 포함)"만 바꾼다. 이벤트 연출의 카메라 이동이 그대로 재현된다.
- 맵 가장자리: 원본은 맵 밖을 보여 주지 않는다. 3D에서는 기울어진 시야 때문에 화면 위쪽이 맵 밖까지 보이므로, 맵 둘레에 바깥 지형(타일 반복 + 어두운 페이드)이나 안개를 둔다.
- 줌·피치 값은 편의 설정에 슬롯 밖 옵션으로 저장한다(기존 편의 설정 방식).

### 3.4 회전을 막는 이유

캐릭터 스프라이트는 4방향(옆·위·아래 + 좌우 반전)뿐이고, 맵 타일 그림은 "북쪽에서 내려다본" 쿼터뷰로 그려져 있다. 카메라를 90° 돌리면

- 캐릭터는 방향 행을 바꿔 그리면 되지만(4방향이라 90° 단위로 깔끔히 맞음),
- 벽·절벽 면(§4.2)은 타일 그림을 그대로 붙인 면이라 옆에서 보면 그림이 찌그러진다.

그래서 1차 목표는 고정 요(악튜러스)다. 맵의 주요 구조물을 3D 모델로 바꾼 맵(§4.4 3단계)만 90° 회전을 켜는 방식으로 라그나로크 쪽에 다가간다. 회전을 켜면 입력도 카메라 기준으로 돌린다(로직은 4방향 그대로, 키 → 방향 매핑만 회전).

## 4. 맵 3D화

### 4.1 원본 맵이 가진 것

`GameMap`: 16px 타일 격자(`tiles`, 타일셋 `t{n}` 8열), 통행 비트(`walk`), 오브젝트 4층(`objBg`, `objLow`, `objMid`, `objTop`, 각각 cmf 프레임 + 몸통 박스), 포털, 액터, 기믹. 높이 정보는 없고, 절벽·벽은 쿼터뷰로 **타일에 그려져** 있다.

### 4.2 핵심 아이디어: 그려진 벽면을 경사면으로 세운다

쿼터뷰 그림에서 높이 h 타일인 절벽은 "윗면 타일 줄" 아래에 "벽면 타일 h줄"로 그려진다. 벽면 줄은 원본에서 통행 불가다.

```
 원본 2D (위에서 본 그림)            2.5D (옆에서 본 단면)
 row 3  ░░░ 윗면(통행)               Y
 row 4  ▓▓▓ 벽면 그림(통행불가)        ▲   ░░░░░░ 윗면: 높이 H, Z = row 3 그대로
 row 5  ▓▓▓ 벽면 그림(통행불가)        │  ╱
 row 6  ··· 아랫면(통행)              │ ╱ ▓▓ 벽면 타일을 이 경사면에 그대로 붙임
                                     │╱
                                     ·········· 아랫면: 높이 0, Z = row 6 그대로
                                     └──────────────────▶ Z (= 원본 y)
```

- 벽면 셀은 원본 위치(Z = row 4~5)에 그대로 두되, 아래 끝은 높이 0, 위 끝은 높이 H인 **가파른 경사면**으로 만든다. 텍스처는 원본 벽면 타일을 그대로 붙인다.
- 그러면 **어떤 셀도 좌표가 바뀌지 않는다.** 판정·포털·이벤트 좌표가 모두 그대로이고, 카메라 피치에서 경사면이 거의 세로로 보여 원본 그림과 비슷하게 읽힌다.
- H는 `벽면 줄 수 × 16 × k`(k ≈ 1.0~1.4, 피치에 맞춰 조정). 윗면 위의 캐릭터는 높이 H에 서므로 화면에서 원본보다 조금 위에 보이지만, 판정은 원본 그대로다.
- 이 변환을 하려면 타일마다 "바닥 / 벽면 / 지붕(윗면이지만 통행 불가) / 물" 분류가 필요하다. 타일셋은 수가 적고(각 8열 격자) 같은 타일셋을 여러 맵이 공유하므로, **타일셋 단위 분류표 한 번**으로 대부분의 맵이 자동 변환된다.

### 4.3 오브젝트 처리

| 원본 층 | 기본 처리 | 예 |
|---|---|---|
| `objBg`, `objLow` | 지형에 붙인 데칼(평면) | 길, 꽃, 바닥 문양, 공간이동석 받침 |
| `objMid` | **세운 판(스탠디)**: 몸통 박스 아래 변을 발 위치로, 카메라 쪽으로 기울인 수직 판 | 나무, 기둥, 상자, 표지판, 포털 표시 |
| `objTop` | 높은 스탠디 또는 지붕 메시. 플레이어가 뒤에 있으면 반투명 | 나무 윗부분, 지붕, 아치 |
| 3D 교체 대상 | 맵 데이터에서 지정한 오브젝트를 저폴리 모델(glTF)로 바꿈. 텍스처는 원본 도트를 그대로 투영 | 집, 성벽, 다리, 큰 바위 |

- 스탠디는 오브젝트 하나당 사각형 하나라 수백 개도 인스턴싱 한 번이면 된다.
- 몸통 박스가 통행 셀을 지우는 규칙(`buildWalk`)은 그대로이므로, 스탠디를 세워도 판정은 원본과 같다.
- 맵 오브젝트 애니메이션(`animateObjects`, 포털 표시의 8프레임 루프)은 텍스처 좌표만 바꾸므로 그대로 동작한다.
- 이벤트·기믹으로 바뀌는 오브젝트(바람 장벽 0x15 → 부서진 장벽 0x3f 등)는 지금처럼 `loadData`에서 바꾼 결과를 그대로 3D로 만든다.

### 4.4 맵 데이터와 단계

맵마다 원본 맵 위에 얹는 **덮어쓰기 데이터** `map3d/<id>.json`을 둔다. 원본 에셋이 아니라 이 프로젝트가 만든 숫자(높이, 분류, 배치)라 저장소에 커밋할 수 있다(원본 그림·맵은 지금처럼 각자 APK에서 생성).

```jsonc
{
  "map": 208,
  "heights": { "cell": [[0,0,0,...], ...] },        // 셀 높이(정점 높이는 주변 평균), 없으면 자동 추정
  "tileClass": { "override": { "12,5": "wall" } },   // 타일셋 분류표를 이 맵에서만 덮어씀
  "objects": { "midIndex:7": { "mode": "model", "model": "house_a.glb" }, "topIndex:2": { "fadeWhenBehind": true } },
  "camera": { "pitch": 50, "zoom": 1.0 },            // 맵별 기본 카메라(던전은 더 내려다보는 식)
  "fog": { "color": "#203040", "near": 300, "far": 700 },
  "lights": { "ambient": 0.8 }                       // 기존 낮/밤 색조(setDayShift)와 곱해짐
}
```

| 단계 | 내용 | 결과 |
|---|---|---|
| 0. 평면 3D | 높이 0, 타일을 바닥에 깔고 objMid를 스탠디로 | 기울어진 카메라의 2.5D 화면이 바로 나옴. 모든 맵 자동 |
| 1. 자동 높이 | 타일셋 분류표로 벽면 줄을 찾아 §4.2 경사면 생성, 윗면 높이 자동 추정 | 절벽·벽이 입체로 섬. 대부분 맵 자동, 일부 수동 보정 |
| 2. 수동 다듬기 | 편집기로 높이 칠하기, 오브젝트 모드 지정, 안개·조명 | 마을·주요 던전 품질 |
| 3. 모델 교체 | 주요 건물·구조물 glTF, 그 맵만 회전 허용 | 라그나로크에 가까운 맵 |

모든 맵이 0단계로 플레이 가능한 상태를 먼저 만들고, 맵 품질은 단계별로 올린다. 3D 데이터가 없는 맵은 0단계로 그린다.

### 4.5 도구

- `tools/build_map3d.py` (또는 TS 스크립트): 원본 맵 + 타일셋 분류표 + `map3d/*.json` → 렌더러가 바로 읽는 메시 데이터(정점 높이, 셀별 면 종류). 빌드 때 `npm run assets` 다음에 돈다.
- **맵 편집기**: 기존 맵 뷰어(`index.html`, `src/web/viewer/`)를 확장한다. 2D 원본 보기와 3D 보기를 나란히 두고 셀 높이 붓, 타일 분류 지정, 오브젝트 모드 지정, 카메라 미리보기, 통행 레이어 겹쳐 보기. 결과는 `map3d/<id>.json`으로 저장(Tauri 데스크톱 앱이면 파일 쓰기 그대로).
- 검증 스크립트: "통행 가능한 셀 사이 높이 차가 문턱값 이상"(캐릭터가 공중에 뜨거나 묻혀 보이는 곳), "경사면이 통행 셀을 덮음" 같은 오류를 맵별로 보고.

## 5. 캐릭터·몬스터·이펙트

- **빌보드**: 원통형 빌보드(Y축만 카메라를 향함)를 기본으로 하고, 카메라 피치만큼 뒤로 기울여 화면에서 원본과 같은 비율로 보이게 한다. 발 위치 = 원본 (x, y), 높이 = `height(x, y)`.
- **방향**: 원본처럼 4방향 + 좌우 반전. 카메라 고정이면 변환 없음. 회전 허용 맵에서는 `(로직 방향 - 카메라 요 / 90°)`로 그릴 방향 행을 고른다.
- **장비 레이어**(무기·머리·갑옷·바지), 틴트(피격 빨강, 독 초록), 페이드, 축소·확대(`scale`)는 `SpriteLayer`가 그대로 처리한다.
- **투사체**: 2D 좌표 그대로, 높이 = 지형 높이 + 원본 그림의 y 오프셋. 화살·마법탄이 언덕을 따라 날아간다.
- **보스**: 큰 보스 스프라이트는 빌보드로 서면 지형·벽에 파묻힐 수 있으므로 깊이 오프셋을 크게 준다. 여러 부위 보스(`spawnParts`)는 같은 깊이 그룹으로 묶어 부위끼리 깜빡이지 않게 한다.
- **스킬 이펙트**: 원본 이펙트 cmf를 그대로 쓰고, 월드에 붙는 것은 빌보드, 대상 색을 읽는 블렌드는 §3.2 이펙트 패스.
- **머리 위 UI**(데미지 숫자, 상태 아이콘, 퀘스트 마크, 말풍선): DOM·UI 레이어 그대로, 위치만 `project(x, y, lift)`.
- **미니맵·지도 탭**: 원본 2D 지도를 그대로 쓴다(라그나로크도 미니맵은 2D).

## 6. 전투: 대쉬 추가

전투 공식·히트박스·AI는 그대로 두고 대쉬만 추가한다. 위치는 `core/combat/player.ts`(로직) + 입력·옵션.

### 6.1 사양(초안, 20 FPS 틱 기준)

| 항목 | 값 | 비고 |
|---|---|---|
| 입력 | 새 가상 키 `DASH`. 키보드 Shift / 패드 L3 또는 키 설정에서 지정, 터치는 오른쪽 버튼 줄에 버튼 하나 | 기존 키 설정 화면(`keyMap.ts`, `bindings.ts`)에 항목 추가 |
| 방향 | 누르고 있는 방향(대각선 포함), 입력이 없으면 바라보는 방향 | 대쉬 뒤 `dir`은 이동 방향의 주축 |
| 거리 / 시간 | 64px(4셀) / 4틱(0.2초), 틱당 16px | 걷기 최대 8px/틱의 2배 |
| 무적 | 처음 3틱 | `vitals.invuln`과 별개 플래그(피격 깜빡임 없이) |
| 쿨다운 | 12틱(0.6초) | 연타 방지. MP·스태미나 소모 없음(필요하면 나중에) |
| 캔슬 | 걷기·대기에서 언제나, 기본 공격은 후딜 구간(콤보 입력 창 이후)에서만, 스킬 시전 중 불가 | 원본 콤보 리듬 보존 |
| 막힘 | 벽·NPC·기믹(`Blockers.solid`)에 막힘, 몬스터(`Blockers.monsters`)는 통과 | 포위 탈출이 목적 |
| 불가 상황 | 이벤트·대화·메뉴, 채집 중(대쉬하면 채집 취소), 기절·둔화(`slowed`)·밧줄 등 이동 제한 상태 | |

### 6.2 구현 포인트

- **터널링**: 틱당 16px은 셀 크기와 같아 한 칸짜리 벽을 뚫을 수 있다. 이동을 4px 단위 하위 스텝으로 나눠 매 스텝 통행 셀·`solid` 박스를 검사하고, 막히면 그 축만 멈춘다(기존 `FUN_000680b4`식 축별 막힘과 같은 방식).
- **포털·트리거**: 하위 스텝마다 검사할 필요는 없다(포털 영역은 셀 여러 개). 기존처럼 틱 끝 위치로 `checkPortals()`.
- **상태**: `Player.action`에 새 값(원본 값과 겹치지 않는 번호)을 쓰고, 애니메이션은 걷기 프레임을 빠르게 + 잔상(같은 프레임을 `fx.alpha`로 2~3장 뒤에) + 출발 지점 먼지 이펙트(기존 이펙트 cmf에서 고름). 새 그림이 필요 없다.
- **카메라**: 대쉬 중 `updateCamera`의 선행 값(`lx`, `ly`)이 커지므로 걷기 속도 기준으로 잘라 카메라가 튀지 않게 한다.
- **옵션**: 편의 설정에 「대쉬」 켬/끔. 2D 버전에서는 기본 끔, 2.5D 버전에서는 기본 켬. 원본 동작 재현이 기본값인 지금 저장소의 원칙과 맞는다.
- **밸런스**: 보스 패턴은 대쉬 없이 설계되어 있어 쉬워진다. 1차는 그대로 두고, 필요하면 하드 모드·3회차·심연에서 무적 틱을 줄인다(2틱). 보스 기록의 「무피격」은 대쉬 사용 여부를 따로 기록할지 결정 필요.
- **테스트**: 하위 스텝 충돌(1셀 벽 통과 불가), 무적 틱 동안 피격 판정 무시, 쿨다운, 캔슬 가능 구간, 이벤트 중 무시 — 모두 `core` 단위 테스트로 node에서 돌린다.

## 8. 성능 예산 (Android 웹뷰 기준)

- 3D 타깃 960×640 이하, 60 Hz 상한(지금 앱 정책 유지).
- 지형: 맵당 메시 1~2개(타일셋 텍스처 하나, 셀 단위 정점). 큰 맵도 정점 수만 개 수준.
- 스탠디·빌보드: 머티리얼별 인스턴싱. 지금의 "레이어당 버텍스 버퍼 하나, 같은 머티리얼 연속 구간은 draw 한 번" 방식을 3D에서도 유지한다.
- 그림자는 그림자맵이 아니라 데칼(지금처럼 사각형 곱하기). 실시간 조명은 쓰지 않고 맵별 주변광 + 기존 낮/밤 색조.
- 측정: 기존 `passes` 카운터처럼 draw call·삼각형 수를 개발자 모드 패널(`devPanel.ts`)에 표시.

## 10. 위험과 대응

| 위험 | 대응 |
|---|---|
| 쿼터뷰로 그려진 타일·오브젝트가 3D에서 어색함(특히 벽면, 지붕) | 카메라 피치를 원본 그림 각도에 맞춤, 회전 금지, 경사 벽면(§4.2). 그래도 어색한 것은 3단계 모델 교체 |
| 큰 스프라이트(보스, 큰 나무)가 지형·벽에 파묻힘 | 빌보드 깊이 오프셋, 발 기준 정렬, 필요한 객체만 깊이 테스트 끔 |
| 원본 블렌드 모드 재현(RGB565 연산) | 고정 함수 가능한 모드는 3D 패스, 나머지는 기존 이펙트 패스 그대로 |
| 판정과 그림의 어긋남(언덕 위 캐릭터가 원본보다 위에 보임) | 판정은 원본 좌표가 정답. 높이 차를 작게(k 조정), 공격 이펙트도 같은 높이 규칙으로 그려 눈으로 보이는 타격 위치를 맞춤 |
| `fieldScene.ts`(2,500줄)의 그리기·로직 혼재로 포크 머지 충돌 | M0에서 그리기 부분을 `FieldRenderer` 뒤로 먼저 분리(이 작업은 이 저장소에 넣어도 동작 변화가 없음) |
| 대쉬로 난이도 붕괴 | 옵션 + 고난도 모드에서 무적 축소, 보스 기록에 대쉬 사용 여부 |
| 맵 수가 많아 수동 작업량 증가 | 0·1단계 자동 변환을 기본으로, 수동 작업은 마을·보스방 위주 |

## 11. 정해야 할 것

1. 저장소: 포크(추천) / 같은 저장소에 렌더 모드 전환.
2. 카메라 회전: 고정(추천, 악튜러스) / 모델 교체 맵만 90° 회전(라그나로크 쪽).
3. 대쉬: 무적 틱·쿨다운 수치, 패드 기본 버튼, 보스 「무피격」 기록과의 관계.
4. 3D 모델 교체(M6)를 할지, 0~2단계(원본 도트만)로 끝낼지.
